# collect_pid の実機レイテンシー

- Date: 2026-11-09

計測環境: macOS 26.5.2 (25F84)、Apple M1 Max (arm64)。`cargo build --release -p procline --example bench` でビルドし、条件ごとに `collect_pid` を初回 1 回、続けて 50 回呼んで最小・中央値・p95 を ms で取った (`crates/procline/examples/bench.rs`)。`icon` は false、`max_ancestors` は 64 (全段) か 0 (対象だけ)。env の値や取得した中身は表示していない。

## 判明した事実

- 全段・env なし・digest なしのウォーム中央値は、端末から 6 段の zsh の列で 13.8 ms、Finder (2 段) 3.5 ms、launchd (1 段) 1.2 ms、ad-hoc 署名のプロセス 1 段で 0.09 ms。zsh の列の初回は 37.9 ms。
- digest を on にすると zsh の列が 42.7 ms、Finder が 19.0 ms に増える。実行ファイルの sha256 が支配的。
- `EnvPolicy::All` と `None` の中央値は同等 (platform binary の env は OS が返さないので、env の費用はこの対象では測れていない)。
- 1 段あたりの費用は一定ではない。zsh の 6 段と 1 段の差は 11.6 ms、Finder の 2 段と 1 段の差は 1.2 ms。段ごとのバイナリ、署名、bundle、ファイルサイズが違う。
- 署名検証だけの費用は分離できていない (署名あり / ad-hoc の対象はプロセス数も取れる情報も違う)。下の表はすべて端から端の比較。

### 署名検証を飛ばした軽い収集 (`CollectOptions.signature: false`、N=50、別の時刻に計測)

| 対象 | 段数 | 署名あり 中央値 ms | 署名なし 中央値 ms |
|---|---:|---:|---:|
| zsh (端末からの祖先。この回は 3 段で `AncestorExited`) | 3 | 6.809 | 1.796 |
| zsh (対象だけ) | 1 | 0.787 | 0.069 |
| Finder | 2 | 2.668 | 0.229 |

署名検証が 1 回の収集の 7〜9 割を占める。署名なしの収集は 1 プロセス 0.07 ms、2 段で 0.2 ms。

## 実用的な示唆

- kawaz の判断 (2026-11-09): 認可は頻繁ではないので、都度の全段収集 (数十 ms) は許容。cw のような常駐型は署名の結果を一定時間キャッシュしてよい。pam-passkey は常駐しないので常に初回の費用だが、50 ms 程度は許容内。
- 収集は段階に分けられる。Touch ID のプロンプトを出す時点で要るのは祖先の名前と path 程度で、`signature: false` の軽い収集 (1 ms 以下) で足りる。全データ (署名、bundle) が要るのは、通知を開いて詳細のページに来た後なので、そこまでに署名ありの収集を終えればよい。

- 認可のたびに全段を集めると、端末のシェルからの要求で約 14 ms (ウォーム)、初回で約 38 ms。digest を含めると約 43 ms。これを毎回払うか、列の一部 (接続相手だけ、または署名だけ) を先に見るかは、UX の要件に照らしてアプリが決める材料。
- 初回が遅い (zsh の列で 1 段だけでも初回 11 ms、以後 2 ms) のは、署名 API の初期化かキャッシュと見ているが内訳は未測定。常駐デーモンなら 1 回払えば済む。
- 内訳 (署名検証、`KERN_PROCARGS2`、bundle の plist、stat) を分けるには `collect_pid` の内部区間の計時が要る。必要になったら feature か環境変数で区間の時間を出す口を足す。

### 測り方の注意

- 「初回」はベンチプロセス内でその対象を最初に集めたときの値で、OS のファイルキャッシュが空の状態ではない。先に測った対象とキャッシュを共有している。
- ad-hoc 署名の常駐バイナリは親が終了して 1 段で `AncestorExited` になり、取れる情報も少ないので、署名検証の純粋な対照群ではない。
- 負荷、対象、測定順序で値は変わる。桁 (1 段 1 ms、6 段 14 ms、digest で 3 倍) を見る材料として読む。
