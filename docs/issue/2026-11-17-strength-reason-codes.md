# 強さの判定を、判定の関数・強さ・理由・コードの 4 つ 1 組で持つ

## 概要

条件の強さ (強 / 中 / 弱) を決める判定の 1 つ 1 つを、判定の関数、結果の強さ、理由、コードの 4 つ 1 組で書く (kawaz 2026-11-17)。画面は、項目の横に強さと理由を出す (DESIGN-ja の設計の柱 5「注意点と強さは伝え、禁止はしない」)。コードをキーにすれば、詳細を書いたオンラインの文書に繋げられる。

理由の文の多言語のリソースは、後で別に扱う (今は決めない)。

## 背景 (事実)

- 今、強さは `Matcher::class` が `Strength` だけを返す。なぜその強さかは返さない
- 保護の状態の判定 (hardened runtime の有無、保護を緩める entitlement、debugged) は、procline-acl の非公開の型 `Protection` の中にある ([issue](2026-11-15-handoff-review-followups.md) の 2)
- 強さが下がる理由は今、少なくとも次がある: 署名を検証できなかった、hardened runtime が無い、保護を緩める entitlement がある (4 種類)、debugged、実行パスを利用者が書ける、祖先だけの条件、項目そのものが弱 (name、cwd、argv、uid など)

## 決めること

- コードの形 (文字列か enum か。名前の付け方。アプリが足す項目の理由のコードをどう分けるか)
- 判定の結果の型 (強さと、理由のコードの列)。1 つの条件に理由が複数ある時の持ち方
- `Matcher::class` の戻り値を変えるか、別の関数にするか (アプリが足す項目の実装への影響)
- コードは公開の約束になる (文書の URL に使う) ので、名前を変えない・重複しないことをテストで保つ仕方
- 注意点 (強さは下げないが伝えたい事実。例: cwd は収集した時点の値) を、同じ仕組みに載せるか
