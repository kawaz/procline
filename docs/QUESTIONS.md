## 裁定待ち

### 👺PL-Q1: depends の pin を match にどう表すか (「矛盾」が何を指すか)

- [ ] a (推奨): match は平坦な map (`key → 値`) のまま。連鎖の構造は Vocabulary が知っている。loader の検査は「欠け」と「JSON の重複 key」で、祖先と葉の値の食い違いは構造上起きない
- [ ] b: 葉ごとに祖先を入れ子で持つ (`"signing_id": {"value": "…", "team_id": "…"}`)。複数の葉が同じ祖先を別の値で持ち得るので「矛盾」の検査が意味を持つ

a の推奨理由: 現行の JSON 例と同じ形で読みやすく、重複・矛盾が起きる余地が無い。b は「矛盾」を検査できる代わりに、同じ値を複数箇所に書かせる。kawaz の「矛盾 (祖先と葉で値が食い違う) はエラー」が b を想定していたなら a では検査対象が消えるので確認したい。関連: [DR-0002](decisions/DR-0002-matcher-depends-and-two-axis-strength.md)

### 👺PL-Q2: `uses` カウンタと `age` → `until` 展開は署名付き一覧の外の可変状態になる

- [ ] a (推奨): どちらも一覧の中に置き、変化のたびにアプリが一覧を書き直して再署名する (`record_use` と preset 適用が一覧の更新になる)
- [ ] b: カウンタは署名外の別ファイル。同じ uid のプロセスが減らして延命できるので、`uses` を持つルールは弱い条件と同じ制約にする
- [ ] c: `uses` を組み込みから外し、必要なアプリが `app.` で足す

a の推奨理由: 一覧の整合が署名 1 つで守られる。書き込み頻度が上がるが、使用のたびに再認証を伴う場面では無視できる

### 👺PL-Q3: `cwd` の glob に書く `~` は誰の home か

- [ ] a (推奨): 接続相手 (対象プロセス) の uid の home。ルールを書く人が「そのユーザーの `~/src`」と読める
- [ ] b: 評価しているデーモンの実行ユーザの home
- [ ] c: `~` を解釈しない (絶対パスだけ)

a の推奨理由: ルールは接続相手を縛るものなので、接続相手の視点の `~` が自然。b は root のデーモンでは `/var/root` になり意図と合わない
